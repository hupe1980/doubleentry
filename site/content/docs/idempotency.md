## The contract

Recording is keyed by `IdempotencyKey`. "Won't duplicate" is not a
specification, so the contract is spelled out:

| Situation | Result |
|---|---|
| Key unseen | Appended |
| Key seen, content **identical** | No-op — returns the original outcome, a safe retry |
| Key seen, content **differs** | Conflict, refused — never a silent overwrite, never a second entry |

```rust
let first  = journal.record(draft.clone())?;
let replay = journal.record(draft)?;

assert!(first.is_new);
assert!(!replay.is_new);
assert_eq!(replay.id,    first.id);
assert_eq!(replay.index, first.index);
```

Note what decides the outcome: whether a resubmission is a safe replay or a
conflict is settled by comparing **content hashes**, not by comparing keys. Two
submissions carrying the same key are the same logical transaction; whether they
say the same thing is a separate question.

## The key is resolved first

The idempotency check runs **before** validation, not after. This ordering is the
whole point.

Consider a retry of an entry that was accepted three months ago. Validation is
against the ledger's *current* accounts, calendar and policy — and in the
meantime its period has been sealed and its account has closed. Validating first
would refuse the retry, turning an at-least-once delivery path into a source of
spurious errors precisely when the ledger is least able to act on them.

**A safe retry must not be able to trip a rule the original submission already
passed.** Resolving the key first is what guarantees that.

## Under concurrency

The uniqueness check has to be part of the write itself, not a preceding read. A
read-then-write races: two concurrent workers both see "key absent" and both
insert.

Both SQL backends therefore claim the key with the `INSERT`, via a unique index
on `idempotency_key`, and interpret the conflict rather than checking first. The
[conformance suite](@/docs/persistence.md#conformance) has a check for exactly
this, and the PostgreSQL tests run concurrent replays of one key against a real
database to confirm it appends once.

## Choosing a key

The key is arbitrary bytes, up to 128 of them, and it is yours to choose. What
makes a good one is that it is derived from the *source* transaction rather than
generated at the point of submission — a message ID, an external document
reference, a `(run, line)` pair from a batch import. A key generated fresh on each
attempt makes every retry a new entry, which is the failure this mechanism exists
to prevent.

## Entry identifiers are separate

`EntryId` is a distinct thing and is checked separately: reusing one with a
different key is a `DuplicateId` error. The identifier is supplied by you rather
than generated by the engine, so that a replay produces byte-identical output —
`EntryId::generate()` exists for callers with no identifier of their own, but it
reads the clock and is therefore not part of the deterministic path.

## Batches

`record_batch` applies entries in order and, if any is refused, undoes everything
that call added — leaving the journal byte-identical to how it started.
Atomicity across entries is not optional: an invoice and the entry that offsets it
must not be separable by a failure partway through.

An idempotent replay *inside* a batch is not a failure. It returns the original
outcome, exactly as a single-entry replay does, and the rest of the batch
proceeds.

```rust
let outcomes = journal.record_batch(vec![already_recorded, brand_new])?;
assert!(!outcomes[0].is_new);
assert!(outcomes[1].is_new);
```
